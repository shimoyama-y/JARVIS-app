# JARVIS の記憶要約・階層化アーキテクチャ

## 目的

JARVIS が会話・調査・問題解決から得た知見を再利用しながら、毎回大量の会話履歴や生ログを AI に渡さずに済む記憶基盤を作る。必要な情報だけを段階的に検索・取得し、トークン消費と運用コストを抑える。

## 現状と目標

現在の JARVIS は、学習履歴・TryHackMe の進捗・セキュリティノート・プロフィールを JSON ファイルで管理し、Google Drive が利用できる場合は同期する。AI のプロンプトにはプロフィールと最近の学習・進捗の短い要約を渡している。

目標はこの仕組みを維持しつつ、記憶を用途と詳細度に応じて三層に分け、短い要約を通常の会話で使い、詳細が必要なときだけ検索で取得できるようにすること。

## 記憶の三層

| 層 | 呼称 | 保存するもの | 利用方法 |
|---|---|---|---|
| Hot | 作業記憶 | 現在の会話・タスクの状態、直近の決定事項、未完了項目 | 現在のタスク中だけ使う。プロンプトに入れる量を上限管理する |
| Warm | エピソード記憶 | 課題、原因、採用した解決策、結果、再利用できる教訓をまとめた短い記録 | タスク完了時に要約して保存。関連する記憶のみ検索し、プロンプトに加える |
| Cold | アーカイブ | 元の会話記録、詳細ログ、関連文書、コード差分など | 通常はプロンプトに含めず、Warm の記録だけでは足りない場合に検索する |

データフロー:

```text
会話・タスクの実行
    │
    ├── 作業中: Hot に現在状態を保持
    │
    └── 完了時: 重要な結果を抽出・要約
                   ├── Warm に構造化エピソードを保存
                   └── 必要な元データを Cold に保存

新しいタスク ──> Hot + プロフィール + 関連 Warm
                            │ 足りない場合だけ
                            └── Cold を検索 (RAG)
```

## Warm 記憶のデータ形式

要約は短く、後で検索・再利用できる構造にする。要約は事実と推測を区別し、認証情報や不要な個人情報を含めない。

```json
{
  "id": "uuid",
  "created_at": "ISO-8601",
  "topic": "問題や作業の短い題名",
  "problem": "解決しようとした課題",
  "approach": "採用した解決策",
  "outcome": "確認できた結果",
  "lesson": "次回に再利用できる知見",
  "tags": ["例: python", "例: debugging"],
  "importance": 1,
  "source_ref": "元ログまたは文書への参照",
  "last_accessed_at": null
}
```

`importance` は 1〜10 の整数とする。保存件数や要約長に上限を設け、重複記録は統合候補として扱う。元データを Cold に保存しない場合、`source_ref` は省略可能。

## 検索とプロンプト組み立て

1. すべての会話履歴ではなく、現在の依頼から検索語・意図を取り出す。
2. プロフィールとタスク状態を Hot として使い、Warm からキーワードまたはベクトル検索で関連記憶を取得する。
3. 関連度、重要度、新しさを使って候補を順位付けする。
4. 上位の記憶だけを、設定したトークン予算内でプロンプトに追加する。
5. 回答に詳細な根拠が必要な場合に限り、`source_ref` を使って Cold の原文を検索する。
6. 検索結果がない場合は、記憶があるかのように振る舞わず、通常の応答を続ける。

ベクトル検索を導入する場合も、まずキーワード検索とメタデータ絞り込みを利用できる形にし、埋め込み生成・検索の費用と遅延を必要性に応じて追加する。

## 要約のタイミングと品質

- タスク完了時、または解決策が検証できた時点でエピソード化する。
- 軽量モデルに要約・タグ付けを任せ、複雑な推論モデルの利用を避ける。
- 要約は「課題・解決策・確認結果・再利用可能な学び」を中心にし、会話の逐語記録をコピーしない。
- 重要度や保存対象を判断できないときは、重要な情報を自動削除せず、既存の明示的な保存機能を優先する。
- 保存に失敗した場合は失敗を通知し、成功したように扱わない。

## 忘却・整理方針

アクセス頻度だけで重要な記憶を自動削除しない。低重要度・重複・古い記憶は、まず統合またはアーカイブ候補にする。削除を自動化する場合は、保持期間、対象範囲、復元方法を定め、ユーザーが設定できるようにする。

## セキュリティとプライバシー

- API キーや認証情報は記憶データに保存しない。必要な秘密情報は環境変数等で管理する。
- クラウドへ送信する会話・ログは必要最小限にする。
- クラウド保存を導入する場合、アクセス制御、通信・保存時の保護、バックアップ、削除方法を確認する。
- ユーザーが記憶の閲覧・修正・削除をできる仕組みを用意する。
- 外部モデルへ要約を依頼する場合、送信対象と費用を明示できるようにする。

## 実装候補

### 段階 1: 現在のローカル記憶を整理

- 既存の JSON 記憶と Google Drive 同期を維持する。
- 会話・タスクの短い状態と、再利用可能なエピソード要約を分ける。
- 既存の `summary_for_prompt()` を基点に、毎回渡す要約量と検索結果の上限を設ける。
- 要約保存・検索・重複判定をテストする。

### 段階 2: Warm 記憶の検索強化

- 最初は既存データのキーワード・タグ検索を利用する。
- ローカルでの検索品質や件数が不足した場合に、埋め込みとベクトル検索を追加する。
- 検索器を差し替え可能にし、現在のファイル保存をすぐに失わないよう移行・バックアップ手順を設ける。

### 段階 3: クラウド DB / ベクトル DB

- Supabase (PostgreSQL + pgvector) などを候補にする。
- エピソード、タグ、作成日時、重要度、参照元、最終アクセス日時を保存する。
- ローカルキューや再送の仕組みを設け、ネットワーク障害で記憶を失わないようにする。
- RLS 等のアクセス制御、鍵管理、バックアップ、データ削除を実装・検証してから有効化する。

## このリポジトリでの実装

- `memory_store.py` の既存 API は維持し、`JARVIS_MEMORY_BACKEND=supabase` のときだけ記憶の読み書き先を Supabase に切り替える。未設定時は現在どおりローカル JSON / Google Drive を使う。
- Supabase Auth のメール・パスワードで認証し、`authenticated` ロールと RLS によりログイン中のユーザー自身の記憶だけを扱う。パスワードや anon key はソースや `settings.json` に保存しない。
- 既存の学習履歴・セキュリティノート・TryHackMe 記録を Warm、プロフィールを Hot として `memory_records` に保存する。会話中のタスク状態は引き続き現在のセッション文脈として扱う。
- チャット・作業・自動操作の依頼ごとに Warm 記憶を Supabase から最大3件検索してプロンプトへ加え、「過去の記録を探す」操作は既存の `recall` コマンド経由で検索する。
- `supabase/memory_tiering.sql` はユーザーごとの RLS、原子的な記録更新、一度限りの旧 JSON 移行、キーワード検索、および `vector(1536)` によるベクトル検索を定義する。
- Supabase 選択時は Gemini 2.5 Flash-Lite で学習エピソードを要約し、Gemini Embedding 2 で Warm 記憶と検索語をベクトル化する。変化していない記録の埋め込みは再利用する。
- 検索はキーワード・タグとベクトル類似度を組み合わせ、上位の Warm 記憶だけをプロンプトに加える。全文会話や添付ファイルは検索 API へは送らず、要約時はメッセージ内の一般的な認証情報表記をマスクする。
- Cold は学習記憶が作られた会話の原文だけを `memory/cold/` にローカル保存し、Warm 記憶に `cold:<UUID>` の参照を付ける。必要な場合は `python jarvis_tools.py memory-source cold:<UUID>` で読み出す。添付ファイルは保存せず、原文は Supabase に送らない。会話ごとのユーザー文・JARVIS 回答はそれぞれ最大 20,000 文字で保存する。
- Gemini に送るのは要約対象の会話だけで、一般的な API キーやパスワード表記は送信前にマスクする。Google の無料枠では入力が製品改善に使われる場合があるため、機微な会話はクラウドバックエンドを有効にしない。

## Supabase 初期設定

1. Supabase プロジェクトを作成し、Authentication でメール/パスワードのユーザーを作成してメール確認を完了する。
2. Supabase Dashboard の SQL Editor で `supabase/memory_tiering.sql` の内容を実行する。
3. JARVIS を起動する Windows ユーザーの環境変数に以下を設定する。`SUPABASE_ANON_KEY` は Project API Keys の publishable/anon key を使い、`service_role` / secret key は使わない。

   ```text
   JARVIS_MEMORY_BACKEND=supabase
   SUPABASE_URL=https://<project-ref>.supabase.co
   SUPABASE_ANON_KEY=<publishable-or-anon-key>
   SUPABASE_EMAIL=<Supabase Auth のメールアドレス>
   SUPABASE_PASSWORD=<Supabase Auth のパスワード>
   GEMINI_API_KEY=<Google AI Studio の API key>
   ```

4. プロジェクトの PowerShell で `.\tools\setup_memory.ps1` を実行する。未設定のパスワードと API キーは非表示入力で求められる。スクリプトは Supabase のスキーマ読み出し、Gemini の埋め込み、要約 API を接続確認し、成功した場合だけ Windows ユーザー環境変数へ保存して `JARVIS_MEMORY_BACKEND=supabase` を有効にする。サービス秘密値は画面やログに表示しない。
5. 新しい PowerShell で `python jarvis_tools.py memory-migrate` を一度実行する。移行はローカル JSON を削除せず、Supabase に既存データがある場合は上書きを防ぐため中止する。
6. JARVIS を再起動する。接続状態だけをもう一度調べる場合は `python jarvis_tools.py memory-check` を使う。設定不足や接続失敗時はエラーを表示し、クラウドを使った成功扱いにはしない。

パスワード/API キーは Windows のユーザー環境変数に保存され、他の同一ユーザー権限のプロセスから参照可能になる。設定変更後は起動済みの JARVIS やターミナルを開き直す必要がある。秘密値の永続保存を避けたい場合は、スクリプトを実行せず、起動ごとに一時環境変数として設定する。

Gemini のモデル名は `GEMINI_SUMMARY_MODEL` と `GEMINI_EMBEDDING_MODEL` で任意に変更できる。既定値は `gemini-2.5-flash-lite` と `gemini-embedding-2`。埋め込みは 1536 次元に固定し、SQL 側の列と一致させる。

Gemini API の無料枠には利用量制限があり、無料枠で送信した内容は Google の製品改善に使われる場合がある。現在の条件は [Gemini API の料金表](https://ai.google.dev/gemini-api/docs/pricing) と [利用規約](https://ai.google.dev/gemini-api/terms) で確認する。キーは環境変数だけに置き、ソース管理へ追加しない。

## コスト管理

- 毎回のプロンプトに含める Hot / Warm の量に上限を設定する。
- Gemini API の無料枠を利用し、無料枠の上限に達した場合はエラーを記録する。課金への自動切り替えはしない。
- 埋め込み生成は新規・更新記録に限定し、重複生成を避ける。
- 無料枠やモデル料金は変更されるため、導入時点の公式価格と利用量で見積もる。

## 成功の確認項目

- 通常のプロンプトに過去の全会話・全ログが入らない。
- 関連する記憶が検索され、無関係な記憶の混入が抑えられる。
- 保存失敗・検索失敗を利用者に分かる形で通知できる。
- ローカル利用時の既存記憶と現在の会話動作が保たれる。
- 保存・検索・上限制御・データ移行を自動テストで確認できる。
